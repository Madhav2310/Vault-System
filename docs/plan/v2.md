## 2. Critical findings

**Retrieval quality has two concrete, fixable defects.** I replayed the stored candidates of the full eval run against gold. This is per-quote recall@8 over all candidates, a stricter measure than the 0.759 per-item number. Recall by ranking:

| Ranking | recall@8 |
|---|---|
| RRF fusion | 0.445 |
| vector only | 0.439 |
| after MiniLM rerank | 0.348 |
| lexical only | 0.123 |

1. **The reranker makes ranking worse** (−0.10). `ms-marco-MiniLM-L-6` is a small web-search model and does not understand contracts or 10-Ks. It also costs latency and has a licence question.
2. **Lexical search barely contributes.** `websearch_to_tsquery` ANDs every term, so a natural question ("What is the governing law of this agreement?") matches almost nothing. It needs OR semantics ranked by `ts_rank_cd`.

**Latency is about 6 s per answer and none of it is streamed.**
- `analyze_query` is a serial LLM call (p50 2.0 s) before retrieval, even on a first question with no history.
- Generation is p50 2.1 s and query embedding 0.5 s.
- The remaining ~1.3 s is reranking and overhead.

**The spec's "AI Insights" pillar is not built.** "Smart Document Analysis", "AI Insights" and "effective prompts for document summarization" are core requirements and a third of the rubric (AI integration, prompt engineering). This is the largest gap, larger than any retrieval point.

**Abstention is unreliable.** `abstain_precision` is 0.50 on smoke: half the abstentions were on answerable questions. There is no evidence gate; the model decides alone.

**The process is over-engineered for the deliverable.** 792 atomic ACs, a convergence engine with Batch API and paired bootstrap, geometry vision QA, DB-scale simulation and a matrix feature are a research program, not a take-home. They cost time that the visible pillars (insights, streaming, docs, demo, UI) need. The eval harness is a strength worth keeping and showing; the tuning machinery around it is not.

**The eval is wasteful.** `make eval-retrieval` runs full generation per item (~$0.70 and 13 min) to measure retrieval. A retrieval-only mode costs about $0.001 and takes ~1 min, which makes iteration 10x cheaper.

**Smaller items:**
- No API rate limiting or quota (a production-readiness bonus).
- No "upload new version of document X" endpoint; versions exist only internally.
- History shows deleted documents' quotes (F-042).
- Cancelled turns stay `running` until the lease expires (F-041).

## 3. Strategy

Win the three rubric thirds with visible, measured features. Every quality claim ships with its regenerate command. Cut depth nobody grades. Order is by impact per hour.

## 4. Tasks

Effort: S ≤ 2 h, M ≤ 0.5 day, L ≤ 1 day. "Check" is the done condition (evidence, not opinion). Lanes marked ∥ can run as parallel worktree agents.

### Phase A — Fix what is measured as broken (retrieval, latency, abstention)

| ID | Task | Effort | Check |
|---|---|---|---|

| A2 | Lexical OR semantics: build an OR tsquery from the query's lexemes (stopwords dropped), rank with `ts_rank_cd`, keep the identifier boost. | S | lexical-only recall@8 rises from 0.12; fused recall does not drop (train split) |
| A3 | Reranker decision, measured on the train split: (a) none (RRF only), (b) `bge-reranker-base`, (c) LLM listwise rerank on `fast` (top 20, ~$0.0003 per turn). Keep the best on recall@8 / latency / cost and record the table in README. | M | Decision table with numbers; test-split confirmation run once |
| A4 | Chunk-prefix check: does embedding `Document/Section/Page` prefixes help? One A/B on train (prefix on/off) via a re-embed of the eval user only. | S | Recorded delta |
| A5 | Skip or parallelise `analyze_query`: no history and ≤ 1 document means a deterministic route (qa) with the raw query; otherwise run analyze concurrently with a speculative retrieval on the raw query. | S | p50 turn latency −1.5 s on smoke; smoke metrics not lower |
