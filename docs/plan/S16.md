### S16.02 — Reranker service: thread, batch and length configuration (root-cause fix)
Deps: S3.11 · Design: §4.3, §7.3 · Files: `reranker/app.py`, `reranker/bench.py`, `reranker/bench_http.py`, `reranker/tests/test_app.py`, `reranker/tests/test_config.py`, `docker-compose.yml`
Do:
1. **`Config` gets four new fields:**
   - `threads`: env `RERANKER_THREADS`, default from `cpu_quota()` capped at 4.
   - `batch_size`: env `RERANKER_BATCH_SIZE`, default 8.
   - `max_in_flight`: env `RERANKER_MAX_IN_FLIGHT`, default **1**, so requests queue rather than oversubscribe the CPU. The semaphore wait still applies.
   - `max_passage_chars`: default **1200**, about 250 tokens. It replaces 8000.
2. **`cpu_quota()` reads the container's CPU quota:**
   - Read `/sys/fs/cgroup/cpu.max`. It contains `max 100000`, or a quota and a period such as `200000 100000`.
   - With a quota, return `ceil(quota / period)`, at least 1.
   - With `max`, or when the file is missing (macOS native), return `min(4, os.cpu_count())`.
   - This is a pure function taking an optional path for tests.
3. **Use the new fields:**
   - `load_scorer` passes `threads=cfg.threads` to `TextCrossEncoder`. `encoder.rerank(query, passages, batch_size=cfg.batch_size)`.
   - The `ThreadPoolExecutor` size is `max_in_flight`.
4. **Long passages are no longer rejected:** a passage over `max_passage_chars` is **truncated by the service** at a word boundary, not rejected with 422. The client side (S16.03) sends focused windows; the truncation is a safety net.
5. **`/healthz`** returns `{status, model, threads, batch_size}`.
6. **`reranker/bench.py` and `reranker/bench_http.py`:**
   - Options: `--threads`, `--batch`, `--words`, `--n`, `--repeats 3`.
   - Prints p50 ms and peak RSS (`resource.getrusage`).
   - Documented in a docstring with the §6 table as the baseline.
   - `bench_http.py` is the same, but over HTTP against the running container (`--url http://localhost:8180`, `--n`, `--requests`). It ends by printing `docker stats --no-stream vault-reranker-1`.
7. **docker-compose:** set reranker env `RERANKER_THREADS=2` to match `cpus: 2`.

### S16.03 — Query-focused rerank windows (client side)
Deps: S16.02 · Design: §7.3 · Files: `backend/app/retrieval/windows.py`, `backend/app/retrieval/retrieve.py`, `backend/tests/unit/retrieval/test_windows.py`
Do:
1. **`focus_window(text, sentences, query, max_words=180) -> str`** (pure):
   - Tokenize `query` into lowercase word stems: regex `[a-z0-9]+`, drop the stopwords in a small module constant, strip a trailing `s`.
   - Score each sentence by the count of distinct query stems it contains.
   - Choose the contiguous window of whole sentences with ≤ `max_words` words that maximizes the summed score. Ties go to the earliest window.
   - If no sentence scores > 0, return the first `max_words` words (FirstP).
   - Never cut mid-sentence unless a single sentence exceeds `max_words`; then cut that sentence at the word limit.
   - Returns text that is a substring of `text` modulo the whitespace between sentences. It is used for reranking only and is never evidence.
2. **In `Retriever._passages`:** load `original_text`, `sentences` and `structural_prefix` (not `embedding_text`). Build the rerank passage as `f"{short_prefix}\n{focus_window(...)}"`, where `short_prefix` is the document title and the last section-path element, ≤ 120 chars.
3. **Config:** `rerank.window_words` (default 180) goes into the next retrieval config (S17.06). Until then, use a module constant `DEFAULT_WINDOW_WORDS = 180`.

### S16.08 — Ingestion concurrency: parallel embedding batches and brief calls
Deps: S16.05 · Design: §6.3, §13.1 · Files: `backend/app/ingestion/embed_index.py`, `backend/app/insights/stage.py`, `backend/app/core/settings.py`, `.env.example`, `backend/tests/integration/ingestion/test_ingest_concurrency.py`
Do:
1. **`EmbedStage`.** Today the batches run one after another (`for i in range(...)`, `embed_index.py`). Run them concurrently, bounded by `asyncio.Semaphore(settings.embed_concurrency)` (default 4).
   - Each batch persists in its own short session, as today, so a failure keeps the finished batches (the stage is idempotent: a rerun embeds only `embedding IS NULL` rows).
   - Use `asyncio.TaskGroup`. On the first failure, cancel the rest and raise the same mapped `StageError` as today.
2. **`generate_brief` map step.** Today the group calls run one after another (`insights/stage.py`). Run them concurrently, bounded by `settings.brief_concurrency` (default 3).
   - **Cost cap:** before starting each group call, reserve its worst-case cost (estimated input tokens plus `max_tokens` at the role's price, via the gateway price table). Do not start a call whose reservation would exceed `brief_max_usd`. Actual spend replaces the reservation when the call finishes.
   - **Order:** results are merged in group order, never completion order, so the output is deterministic.
3. **Gateway rate limits are respected:** use the gateway's existing limiter and check that nothing bypasses it.
4. **Measure** time-to-ready for the AMD 10-K and for a 10-page PDF before and after, with the FakeProvider latency profile (0.5 s per call) for repeatability. Record it in progress.md.
