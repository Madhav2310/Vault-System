# Vault Wins by Making Its Citations Visible

Vault already has the hardest part of a trustworthy document-chat product, and it is better built than anything in the open-source field. Its citations are sentence-level handles. The model echoes a handle, and code copies the stored sentence into the answer. That gives the same "valid pointer" guarantee as Anthropic's Citations API, keeps strict structured outputs (which Anthropic's feature cannot do), and is finer-grained than RAGFlow, Onyx, Kotaemon, LlamaIndex or Haystack. The problem is that a reviewer spending **5-20 minutes** on the submission cannot see any of this: there is no UI, no streaming, and the README is weak. The 792-acceptance-criterion plan and the infrastructure sprawl look like the over-engineering that reviewers reject. The work with the highest return is therefore presentation and focus, not new retrieval science. Ship a thin streaming UI where every claim can be checked with one hover. Give "not found" and "unsupported" explicit states. Rewrite the README and record a demo for a reviewer who has minutes. Report the evals with error bars. On retrieval, the best-supported cheap gains are four: fix the reranker or take it off the request path; route document-scoped questions to whole-document context; put contextual prefixes into the full-text index; and replace bare `ts_rank` with a normalized, field-weighted variant. Almost every headline gain number in retrieval and citation tooling is vendor-reported, so only Vault's own 122-item golden set, read with paired statistics, should decide what ships.

## Reviewers grade a running core in minutes, not a plan

The take-home evidence is thin but consistent. Gergely Orosz, writing first-hand as a hiring manager (in 2019, the most specific source available), says reviewers first ask "Does it work at all?" and whether they can run it from the setup notes. He spends **5-20 minutes per submission**, and documentation "is such a miss on 80% of submissions." Good READMEs state what was built, what was deliberately not built, why the main decisions were made, and what comes next ([Orosz](https://dev.to/gergelyorosz/9-insider-tips-to-ace-your-next-takehome-project-for-frontend-fullstack-and-mobile-interviews-41nn)). Sloppy handling of basic edge cases is "one of the most common reasons" working submissions get rejected (same source). Candidate reports name the opposite failure as well. One Expensify submission was "rejected because I was told that my solution was over-engineered" ([Glassdoor, via search snippet](https://www.glassdoor.ca/Interview/Expensify-com-Interview-Questions-E254791.htm)). In a 2025 case, a fully AI-generated solution came out "overly complicated", and the candidate only succeeded after rolling it back and building a simpler base ([Formation](https://formation.dev/blog/how-technical-interviews-are-evolving-with-ai)). One reviewer describes the passing project as the one with "keyboard shortcuts for everything": polish and tight scope beat ambitious design documents ([HN](https://news.ycombinator.com/item?id=43982643)). The spec's own line, "a fully functional subset over partially implemented features", says the same thing.

On AI-first development, which is a third of the grade, the clearest public rubric is Canva's. It asks whether candidates "understand when and how to leverage AI effectively" and "can identify and fix issues in AI-generated code". Its strongest candidates "used AI strategically for well-defined subtasks while maintaining control of the overall solution" and "didn't just prompt AI and accept whatever it generated" ([Canva Engineering, 2025](https://canva.dev/blog/engineering/yes-you-can-use-ai-in-our-interviews)). No public AI_USAGE.md template exists. The strongest format follows Canva's criteria: organize it by decision rather than by tool, and include a short "where the AI was wrong and how I caught it" section. Raw prompt logs score lower than curated judgment calls. About **32%** of candidates in an interviewing.io survey were told their code would be discussed in a later round ([interviewing.io](https://interviewing.io/blog/why-engineers-dont-like-take-homes-and-how-companies-can-fix-them)). Every piece of machinery in Vault has to be defensible in a live walkthrough. Anything that isn't is a liability, not a credential.

That changes how Vault should present itself. Reviewers never read the 792-AC plan, the convergence engine, hash-partitioned `chunks`, the grafana/otel-lgtm stack or Locust. They see a repo, a README and a demo. Published submission rules cap demos at about **5 minutes**, with 3-4 minutes as the stated ideal ([Pulp](https://pulp.plan.io/projects/pulp/wiki/Demo_Presenter_Notes/10/annotate); [medblocks](https://medblocks.com/training/courses/fhir-app-challenge/41-submission)). The popular open-source reference, Kotaemon (about 25.9k stars), sells itself with live demos and citations highlighted in an in-browser PDF viewer, and ships no eval table ([Kotaemon](https://github.com/Cinnamon/kotaemon)). A demo that shows the core flow in the first 60 seconds, plus an eval table with a regenerate command, would put Vault above that bar. The README should follow the reviewer's order:

1. A one-paragraph summary and the video link.
2. One-command start and seed.
3. The spec's feature list, marked done or deferred.
4. An architecture diagram.
5. Decisions and cuts.
6. The eval table with `make` commands and dollar cost.
7. Measured scale notes for thousands of documents.
8. curl examples.
9. A link to AI_USAGE.md.

## Deterministic citations are the product, so make them checkable in one hover

### The field is still guessing, and Vault is not

The open-source projects range from probabilistic to deterministic citation. RAGFlow's basic pipeline embeds each answer sentence and attaches chunks by cosine similarity, lowering a threshold from 0.63 by a factor of 0.8 each round. Its own code comment says that path "earns its [ID:N] markers two probabilistic ways", and its newer agentic path makes code extract echoed chunk ids, with unresolved ids left "unmarked rather than pointing at a wrong index" ([RAGFlow citations.go](https://raw.githubusercontent.com/infiniflow/ragflow/main/internal/agentic_rag/citations.go); [citation.go](https://raw.githubusercontent.com/infiniflow/ragflow/main/internal/service/citation.go)). Kotaemon asks the model for start and end phrases and matches them with `difflib`. In the PDF viewer it highlights any text-layer span whose fuzzy match ratio exceeds 0.5 ([Kotaemon utils.py](https://raw.githubusercontent.com/Cinnamon/kotaemon/main/libs/kotaemon/kotaemon/indices/qa/utils.py); [pdf_viewer.js](https://raw.githubusercontent.com/Cinnamon/kotaemon/main/libs/ktem/ktem/assets/js/pdf_viewer.js)). LlamaIndex and Haystack map `[n]` markers to chunks ([LlamaIndex](https://developers.llamaindex.ai/python/examples/query_engine/citation_query_engine/); [Haystack AnswerBuilder](https://raw.githubusercontent.com/deepset-ai/haystack/main/haystack/components/builders/answer_builder.py)). Among vendors, OpenAI's `file_search` annotations carry only `file_id`, `filename` and an index, with no quoted span or page ([OpenAI file search](https://developers.openai.com/api/docs/guides/tools-file-search)). Google Vertex no longer returns grounding confidence scores for Gemini 2.5 and later ([Vertex grounding](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/grounding/grounding-with-vertex-ai-search)).

Anthropic's Citations API is the closest analogue to Vault. It splits documents into sentences, extracts `cited_text` itself so that "citations are guaranteed to contain valid pointers", and treats custom content blocks "as-is", which is effectively Vault's handle scheme. But it "cannot be used together with structured outputs", and scanned PDFs "are not citable" ([Anthropic Citations docs](https://platform.claude.com/docs/en/build-with-claude/citations)). Vault's combination of handles, a strict schema, code-copied text and dropped unknown handles is the deterministic end of this spectrum, at sentence granularity. That justifies staying on application-managed citations rather than OpenAI's hosted vector stores. It also belongs in the README's first screen, because it removes the most-reported failure in this product category: a citation that doesn't match its source ([NotebookLM complaint write-up](https://horadecodar.com.br/notebooklm-erra/); [OpenAI community](https://community.openai.com/t/pdf-page-identification-errors-with-file-search-on-assistants-v2-api-paging-problem-pages-not-in-chunk-metadata/793805)).

### A valid pointer is not a supporting citation

Code-copied quotes eliminate fabricated quotes. They do not eliminate wrong-span or non-supporting citations, and those are common. Liu et al. found that only **74.5% of citations supported their sentence** across four generative search engines, and only 51.5% of sentences were fully supported ([arXiv 2304.09848](https://arxiv.org/abs/2304.09848)). ALCE found that even the best models lacked complete citation support about **50%** of the time on ELI5 ([ALCE](https://arxiv.org/abs/2305.14627)). Wallat et al. found that up to **57%** of citations can be correct yet unfaithful, meaning they were rationalized after the fact rather than used ([arXiv 2412.18004](https://arxiv.org/abs/2412.18004)). The remaining risk is support, and the remedy is a per-claim entailment check of each answer sentence against its cited sentences. The premises are short, which is where small checkers do best. MiniCheck-FT5 (770M parameters, EMNLP 2024) "reaches GPT-4 accuracy" on LLM-AggreFact at roughly 400x lower cost ([MiniCheck](https://arxiv.org/abs/2404.10774)). Vectara's HHEM-2.1-Open runs in under 1.5 s on CPU for a 2k-token pair, but that is vendor-reported, and its balanced accuracy falls to about **52.6%** on the adversarial FaithBench ([Vectara](https://www.vectara.com/blog/hallucination-detection-commercial-vs-open-source-a-deep-dive)). Either one is a flagging signal, not ground truth. Under Vault's "no new service" rule, start with a fast-role judge through `app.llm.gateway`, emit a `CITATION_WEAK_SUPPORT` reason code, and add a local checker only if it wins on the golden set.

Abstention has to be owned by code. Google's Sufficient Context study (ICLR 2025) found that large models "often output incorrect answers instead of abstaining when the context is not" sufficient. Selective generation using a sufficiency signal improved accuracy on answered questions by only **2-10%** ([Joren et al.](https://arxiv.org/abs/2411.06037)). That is the realistic ceiling to quote. Vault's gate should combine three signals:

1. A retrieval signal, such as the top score and its margin over the next result.
2. A typed `sufficient: yes/partial/no` decision from a cheap model.
3. The citation-resolution outcome, with no resolved handles meaning abstain.

Code applies the result, and a reason-code template explains it. A "partial" state, which answers the covered part and flags the rest, is likely better UX than binary refusal. That is an inference, not a finding from the paper.

### Trust UX means cheap verification, not persuasion

The interface patterns have converged. NotebookLM's citations are "a specific block of text from your source", previewed on hover and opened in context on click ([NotebookLM Help](https://support.google.com/notebooklm/answer/14276569?hl=en); [Google blog](https://blog.google/technology/ai/notebooklm-new-features-availability/)). Glean added deep-linked citations because document-level links were too coarse ([Glean](https://docs.glean.com/user-guide/assistant/glean-chat/glean-chat-citations/deep-linked-citations)). Harvey and Elicit cite each cell of a comparison grid ([Harvey](https://help.harvey.ai/articles/using-review-tables); [Elicit](https://support.elicit.com/en/articles/4267649)). The HCI evidence explains why exact quotes matter more than fluent prose. In a pre-registered CHI 2025 study (N=308), explanations increased reliance on both right and wrong answers, while showing sources reduced reliance on wrong ones ([Kim et al.](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies)). Another study found that **random citations still raised trust**, and checking them lowered it ([arXiv 2501.01303](https://fugumt.com/fugumt/paper_check/2501.01303v1_enmode)). So the citation's presence persuades, and only verification calibrates trust. Across eight AI search tools, the Tow Center found more than 60% of answers wrong and the tools "generally bad at declining" ([Nieman Lab](https://www.niemanlab.org/2025/03/ai-search-engines-fail-to-produce-accurate-citations-in-over-60-of-tests/)). A well-designed "not found" state is therefore a differentiator, not an admission of weakness.

For Vault, that adds up to a short build list:

- Terse answers with an inline `[n]` on every claim.
- A hover card showing the exact stored sentence, document and page.
- A click that opens a side panel scrolled to that sentence and highlighted. A plain text view first; a pdf.js page is a stretch goal.
- Unresolved or weakly supported claims shown as "unsupported" rather than silently dropped.
- A "Not found in your documents" state that names what was searched and offers rephrase, widen scope, or show closest passages.
- Per-document status (queued → parsing → indexing → ready, or failed with retry).
- A scope selector: this document, selected documents, or all.
- The existing cited brief, shown as a "source guide" card with suggested questions, the moment a document finishes processing.

Summary customization should use presets (brief, detailed, key risks, timeline), following NotebookLM's preset-and-mode pattern, rather than free-form prompt editing ([Google help index](https://support.google.com/notebooklm/answer/14290935)). Avoid numeric confidence badges: no evidence shows they help, and the random-citation result shows that trust signals can mislead ([Lajewska & Balog](https://arxiv.org/abs/2601.14460v1)). Tables cited from documents should render as small tables, since Glean concedes its flattened table citations are hard to read ([Glean](https://docs.glean.com/user-guide/assistant/glean-chat/glean-chat-citations/deep-linked-citations)).

Streaming is the main fix for the 6-second answer latency. Show real pipeline stages before the first token ("Searching 3 documents" → "Reading 8 passages" → "Writing"), never a fake spinner. The classic 0.1 s / 1 s / 10 s attention thresholds are the only anchor. Specific time-to-first-token targets online are unsourced practitioner claims ([Redis](https://redis.io/blog/ttft-meaning/)). Onyx's MIT-licensed `citation_processor.py` is the reference design for turning citation markers into links during a stream. It is an incremental, code-fence-aware parser with a number-to-document map ([Onyx](https://raw.githubusercontent.com/onyx-dot-app/onyx/main/backend/onyx/chat/citation_processor.py)). One open question is UNKNOWN: whether Vault's strict-schema answer can stream as partial JSON on the current OpenAI Responses API. Check the current docs before choosing between streaming handles inline and streaming stage events followed by the validated answer.

## Route by scope, then fix the retrieval legs that are broken

### Whole documents beat top-k chunks when the scope fits

The strongest retrieval evidence is not about rerankers. It is about not retrieving at all when the user has already named the document. In Google DeepMind's Self-Route study, long context beat top-5 RAG by **49.70 vs 37.33** (Gemini-1.5-Pro) and **48.67 vs 32.60** (GPT-4o). A router reached about long-context quality at **39-65% lower cost**, and both modes gave identical predictions on about 63% of queries ([Self-Route](https://arxiv.org/html/2407.16833v2)). On FinanceBench, GPT-4-Turbo got **79%** right with the filing in context, against **19%** with a shared vector store ([FinanceBench](https://arxiv.org/abs/2311.11944v1)). Anthropic advises that a knowledge base under 200k tokens can skip RAG ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). The opposing evidence is real. Chroma's Context Rot study of 18 models found focused prompts of about 300 tokens beat full prompts of about 113k tokens for every model ([Chroma](https://www.trychroma.com/research/context-rot)). Databricks found only a handful of top models stay consistent above 64k tokens ([Databricks](https://arxiv.org/html/2411.03538v1)). The design that fits both is a router owned by code, not by the model, which keeps Vault's "LLM never picks control flow" rule. When the scope is one or a few documents under roughly 100k tokens, pass them whole as handle-tagged sentences. For vault-wide questions, use hybrid retrieval. Handles keep citations deterministic in both modes.

At third-party prices that have not been verified against OpenAI, a 100k-token document costs about $0.10 per question uncached on the balanced role and about $0.005 per cached follow-up ([morphllm pricing mirror](https://www.morphllm.com/openai-api-pricing)). That is my arithmetic, and the latency of 100k-token prompts on these models is unmeasured. Both need a sampled run under `--max-usd` before the router ships.

### Contextual prefixes help the keyword leg most

Anthropic reports that contextual embeddings cut its top-20 retrieval failure rate from **5.7% to 3.7%**. Adding contextual BM25 takes it to **2.9%**, and reranking on top to **1.9%**, at a one-time cost of **$1.02 per million document tokens** using Claude 3 Haiku with prompt caching ([Anthropic](https://www.anthropic.com/news/contextual-retrieval)). These are vendor numbers, averaged across embedders, on codebases, fiction and papers, with no contracts or filings. The only rerun I found is also vendor-run. It shows the largest gain on the keyword side, where recall@20 rose from **70.48 to 89.26**, against 90.06 to 94.48 for vectors ([Denser AI](https://denser.ai/blog/compare-open-source-paid-models-anthropic-dataset/)). Onyx ships the same idea in production, with a reserved contextual-RAG token budget and separate semantic and keyword metadata suffixes per chunk ([Onyx chunker.py](https://raw.githubusercontent.com/onyx-dot-app/onyx/main/backend/onyx/indexing/chunker.py)). For Vault, the generated context must go only into the embedding input and the `tsvector`, never into `original_text`. That keeps the evidence invariant intact. At the unverified fast-role price, my rough re-costing comes to about **$0.40 per million document tokens, or about $8 one-time for 1,000 twenty-thousand-token documents**. That number belongs in the README's scale section.

### `ts_rank` is not BM25, and the reranker is not running

Postgres `ts_rank` has "no term saturation, no length normalization, no native IDF" ([Microsoft Learn](https://learn.microsoft.com/azure/horizondb/ai/full-text-search)), and it scores every matching row before `LIMIT` ([ParadeDB](https://www.paradedb.com/blog/benchmarker-iteration)). The cheap fix needs no new dependency. Use `ts_rank_cd` with a length-normalization flag, and give titles and section headings higher weight with `setweight`. True-BM25 extensions exist (pg_textsearch, ParadeDB pg_search, VectorChord-bm25), but every comparative benchmark for them is vendor-run ([Tiger Data](https://tigerdata.com/blog/pg-textsearch-bm25-full-text-search-postgres)). Keep them as a documented scale path. On fusion, RRF beat BM25 alone by about 18% on BEIR and added 1.4% over a strong learned-sparse retriever ([Elastic](https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid)). One third-party test found score-normalized fusion **3.86%** better than RRF on six BEIR datasets, though it needs per-dataset tuning ([BigData Boutique](https://bigdataboutique.com/blog/hybrid-search-fusion-methods-compared)). Onyx uses min-max weighted fusion at 0.5/0.5 ([Onyx search.py](https://raw.githubusercontent.com/onyx-dot-app/onyx/main/backend/onyx/document_index/opensearch/search.py)). Keep RRF unless a weighted variant wins a paired test on the train split.

A reranker that times out in 79% of runs contributes latency and nothing else. The measured 1.3-2.6 s for 40 passages works out to roughly 15-30 pairs per second. Sentence-Transformers lists MiniLM-L6 at **1,800 docs/sec** (hardware unstated), with L4 at 2,500 and L2 at 4,100. The nDCG@10 cost of those smaller models on TREC DL19 is 1.3-3.3 points (74.30 → 73.04 → 71.01) ([SBERT](https://www.sbert.net/docs/cross_encoder/pretrained_models.html)). A gap that large points to a configuration problem rather than the model: long pairs truncated at 512 tokens, container threading, or no ONNX/int8. This is an inference. The three experiments are cheap: cap each pair at about 256 tokens (the query plus the best-scoring sentence window), use ONNX int8, and try L4. Larger rerankers are not a fix. Even on an A100, bge-reranker-v2-m3 takes **3.05 s** per query and mxbai-rerank-large-v2 **0.89 s**, and their BEIR advantage (57.49 vs 53.94 nDCG@10) is self-reported ([Mixedbread](https://mixedbread.com/blog/mxbai-rerank-v2)). If the fixes don't bring p95 under a few hundred milliseconds, take the reranker off the request path. Anthropic's own numbers put contextual BM25 ahead of reranking as the larger step. An LLM listwise reranker on the fast role is cheap in tokens, but PaperQA2's ablation is a warning: a weaker model doing relevance scoring did *worse than no scoring at all* ([PaperQA2](https://arxiv.org/html/2409.13740)). It has to win a paired test before it ships.

Several popular techniques should be skipped. HyDE's large published gain is over an unsupervised embedder (Contriever 44.5 → 61.3 nDCG@10 on DL19). It merely ties a supervised retriever (62.1), and Vault already uses one ([HyDE summary](https://finisky.github.io/en/hyde-paper-summary/)). One single-author blog reports query decomposition at +11 recall points on multi-hop questions and −5 on lookups. That is anecdotal, and it justifies decomposition only for comparison intents detected by code ([DEV](https://dev.to/gabrielanhaia/hyde-multi-query-decomposition-which-query-rewrite-actually-moves-recall-1m08)). Metadata filters resolved from the query (document, period, entity) are the likelier win, because many FinanceBench failures were wrong-filing retrievals. That is an inference I have not measured. On chunking, Chroma found that overlap hurt efficiency, and its 400-token, zero-overlap chunks scored **89.5** recall against 85.4 for OpenAI's 800/400 default ([Chroma chunking](https://www.trychroma.com/research/evaluating-chunking)). Onyx sets overlap to zero because "we need a clean combination of chunks" ([Onyx](https://raw.githubusercontent.com/onyx-dot-app/onyx/main/backend/onyx/indexing/chunker.py)), and RAGFlow has an open bug where overlap drops highlight coordinates ([RAGFlow #18148](https://github.com/infiniflow/ragflow/issues/18148)). Use small structure-aware chunks, keep tables whole as their own chunks, and expand to the section or page for the generator.

On scale, a vault of thousands of documents is roughly 100k-1M chunks. That is modest for pgvector, where halfvec halves storage ([AWS](https://aws.amazon.com/de/blogs/database/load-vector-embeddings-up-to-67x-faster-with-pgvector-and-amazon-aurora/)). The text-embedding-3-small to -large gap is only 2.3 MTEB points in English but 10.9 on multilingual MIRACL ([Pinecone](https://www.pinecone.io/learn/openai-embeddings-v3/)). Report a measured ingest throughput and the per-document cost. Don't assert partitioning as a necessity.

### Keep the glyph stream and borrow structure only

Parsing benchmarks contradict each other. OmniDocBench v1.0 ranks Docling well below Marker and MinerU ([OmniDocBench](https://arxiv.org/pdf/2412.07626)). OpenDataLoader, itself a competitor, ranks Docling above both, with table TEDS of 0.887 against 0.401 for PyMuPDF4LLM ([OpenDataLoader](https://opendataloader.org/docs/benchmark)). Licenses settle most of the choice:

| Parser | License | Fit for Vault |
|---|---|---|
| pdfplumber | MIT | Keep as the evidence source |
| Docling | MIT | Optional structure source |
| PyMuPDF | AGPL | Poor fit for a service |
| Marker | Apache-2.0 code; weights under a revenue-capped RAIL-M license | Commercial limits |
| MinerU | Apache-2.0 plus thresholds | Commercial limits |

Sources: [pdfplumber](https://github.com/jsvine/pdfplumber), [Docling](https://github.com/docling-project/docling), [pymupdf4llm](https://github.com/pymupdf/pymupdf4llm), [Marker](https://github.com/datalab-to/marker), [MinerU](https://github.com/opendatalab/MinerU).

Only low-level libraries expose per-character coordinates. Docling's provenance stops at item-level bboxes and charspans ([docling-core](https://github.com/docling-project/docling-core/blob/main/docling_core/types/doc/document.py)), so it cannot replace Vault's glyph-mapped stream for sentence-exact highlights. It runs at about 1.3-2.2 pages/s on an M3 Max without OCR, and TableFormer takes 2-6 s per table on CPU ([Docling report](https://arxiv.org/html/2408.09869)). The right role for Docling is optional: a layout and table oracle whose output is reconciled onto pdfplumber's characters, and only if it wins on `make eval-extraction`. Two failure modes deserve explicit handling. First, scanned pages should be flagged at upload, since pdfplumber does no OCR. Second, DOCX tracked changes. Pandoc documents `--track-changes=accept|reject|all` ([Pandoc](https://pandoc.org/MANUAL.html)), while python-docx's changelog shows no revision support ([HISTORY](https://github.com/python-openxml/python-docx/blob/master/HISTORY.rst)). The suspicion that python-docx silently drops text inside `w:ins` is unverified. A fixture test settles it cheaply.

## Credible evaluation at n=122 means paired tests and calibrated judges

Vault's golden set and deterministic graders are its strongest technical evidence, but single-run numbers overstate what 122 items can show. Evan Miller's framing, "evaluations are experiments", fits ([Miller](https://arxiv.org/abs/2411.00640)). By my arithmetic, recall@8 of 0.74 on 122 items carries a 95% interval of about **±7.8 points**, and slices of 30-40 items per source widen it to ±13-15. The 97% brief-verification figure, measured on 3 documents, should be reported as a count of facts with an interval, not as a rate. Only paired comparisons resolve few-point tuning deltas. With 10 discordant items, McNemar needs about **9-1** to reach p<0.05. A paired bootstrap over stored per-item scores costs no API spend. Report the discordant counts alongside the two accuracies.

Judges need calibration in the open. Hamel Husain and Shreya Shankar recommend starting "with error analysis, not infrastructure", using binary pass/fail, and validating any judge "against human labels before trusting its decisions" ([Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Thakur et al. show that "judges with high percent agreement can still assign vastly different scores", so report kappa or TPR/TNR, not raw agreement ([Thakur et al.](https://arxiv.org/abs/2406.12624)). Framework metrics are fragile. GroUSE found that RAGAS and DeepEval faithfulness results "differ significantly due to differences in the prompts" ([GroUSE](https://arxiv.org/pdf/2409.06595)). One practitioner saw the same fabricated answer score 0.0 on one and 1.0 on the other, though that is anecdotal ([DEV](https://dev.to/nickjlamb/we-gave-the-same-fabricated-answer-to-ragas-and-deepeval-one-scored-it-00-the-other-scored-it-10-57om)). OpenAI says it is "deprecating graders as part of the evals and fine-tuning workflows" ([OpenAI graders](https://developers.openai.com/api/docs/guides/graders)), so local graders through the gateway are the durable choice. Vault's judge and generator are both OpenAI models. Disclose that, keep judge tasks narrow ("does E3.1 support claim X?"), and spot-check about 20 items through the dormant Anthropic adapter to measure cross-family disagreement.

The metrics worth reporting map onto published practice:

- **Citation precision and recall**, ALCE-style ([ALCE](https://arxiv.org/abs/2305.14627)).
- **Cited-claim precision**, as PaperQA2 measured it: 86.1% against Wikipedia's 71.2% on WikiCrow ([PaperQA2](https://arxiv.org/html/2409.13740)).
- **Evidence-sentence recall against gold evidence**, which QASPER's Evidence F1 models directly ([QASPER](https://huggingface.co/papers/2105.03011.md)).
- **Abstention accuracy on unanswerable items.**
- **Latency at p50/p95.**
- **Dollars per answer.**

Every number should ship with its `make` target, model, prompt version and seed. Per-source scores should be framed against the 2023 baselines, not as leaderboard claims. For example, "N FinanceBench items, seed S, X% ± CI, against the paper's 19% shared-store and 79% long-context results." Shankar's "criteria drift" finding argues for revising the golden set from observed failures while keeping the test split frozen ([Shankar et al.](https://arxiv.org/pdf/2404.12272)).

## Plain typed stages and hand-set GenAI telemetry are the architecture story

Vault's hard rules already match the most-cited practitioner guidance, and the README should say so. Anthropic recommends "predefined code paths" over autonomous agents, warns that frameworks "obscure the underlying prompts and responses", and advises starting "by using LLM APIs directly" ([Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). 12-Factor Agents' "own your prompts" and "own your control flow" describe Vault's versioned prompt files and typed decisions ([12-factor agents](https://github.com/sahanatvessel/12-factor-agents)). Eugene Yan lists evals, guardrails and defensive UX among the core patterns ([Eugene Yan](https://eugeneyan.com/writing/llm-patterns/)). The frameworks would not help with Vault's hardest part anyway, since LlamaIndex and Haystack only cite at the `[n]`-to-chunk level. The structure to show a reviewer is one module per stage, each a typed function. One gateway handles all model calls, and Pydantic models serve as both the strict schema and the internal type. Each stage gets one span, and every span and eval row records `prompt_id@version`, digest, model, reasoning effort and schema version.

For observability, the OpenTelemetry GenAI conventions are still entirely at Development stability. In v1.42.0 (June 2026) they moved to a separate repo that has no tagged release, and the token metrics were reorganized again in September 2026 ([John Hodge, Nov 2026](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/)). The safe path is to set the long-lived attributes by hand in the gateway: `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, and `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens`. Add a custom `vault.cost_usd` for cost, since the conventions don't define one. The conventions' default content-capture setting is NO_CONTENT, which matches Vault's IDs-and-digests rule and is worth stating as conformance. The metrics API the spec asks for should expose what users and reviewers care about: documents by status, ingest throughput, answer latency, abstention rate, unsupported-claim rate and cost per answer, with only bounded enum labels.

A few other open-source patterns are worth borrowing as ideas. Onyx splits its Celery workers into separate apps (`light`, `heavy`, `docfetching`, `docprocessing`, `beat`, `monitoring`) so that parsing never starves interactive tasks ([Onyx celery apps](https://github.com/onyx-dot-app/onyx/tree/main/backend/onyx/background/celery/apps)). That is the cheapest credible answer to "how does this scale to thousands of documents". open-notebook keeps its job queue in the database rather than in a broker ([open-notebook](https://raw.githubusercontent.com/lfnovo/open-notebook/main/commands/source_commands.py)), which supports Vault's `processing_jobs` design. Code can be lifted only from MIT or Apache files, with headers kept. Khoj (AGPL), Morphik (BSL 1.1) and Onyx's `ee/` directory are off-limits ([license survey](https://github.com/morphik-org/morphik-core)). Project status is a lesson too. Verba is archived, R2R has had no pushes for about a year, and RAGFlow rewrote itself from Python to Go, so 2024-era tutorials based on their code are stale ([Verba](https://github.com/weaviate/Verba); [R2R](https://api.github.com/repos/SciPhi-AI/R2R)).

## Conclusion

The research changes where the effort should go. Vault set out to beat the field on retrieval and process rigor. The evidence says its real lead is a citation architecture that the field is only now converging on: RAGFlow's 1.0 rewrite moved independently toward code-extracted ids for the same reason. What the field still lacks is a UI that lets users check each citation. In-product verification is the scarce thing. The HCI work shows citations persuade even when random, so the product that wins trust makes checking the sentence cheaper than believing it. That reframes "explainable" for Vault: not model-written explanations, which raise reliance on wrong answers, but deterministic evidence, visible "unsupported" and "not found" states, and reason codes.

The second shift is that the cheapest retrieval gains come from routing and repair, not new models. Whole-document context for document-scoped questions, a reranker that runs or is removed, a keyword leg with length normalization, and keyword-side contextual prefixes all fit the existing stack without a new service. Each is decidable on the existing golden set with a paired test. The same discipline applies to the process. A reviewer with fifteen minutes will judge Vault by what runs, what's visible, and how honestly the numbers carry their error bars, not by how many acceptance criteria were ticked.
